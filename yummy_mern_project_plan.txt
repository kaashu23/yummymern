================================================================================
     MERN RESTAURANT WEBSITE "YUMMY" — FULL PROJECT PLAN (PORTFOLIO)
================================================================================

PROJECT OVERVIEW
----------------
A full-stack, responsive restaurant web application built with the MERN stack,
scaled up from the static "Yummy" GSAP/Locomotive Scroll landing page. This is
designed as a genuine restaurant/hospitality webapp — NOT an ecommerce store.
The core experience centers on table reservations, showcasing the menu, chefs,
events, and gallery, with an optional lightweight takeaway/delivery ordering
add-on (secondary feature, not the main flow). Includes an admin dashboard to
manage reservations, tables, menu, events, chefs, gallery, and testimonials,
Clerk authentication, ImageKit image storage, Sentry error tracking, Nodemailer
email confirmations, and full dark/light theme support. GSAP + Locomotive
Scroll animations are preserved on the frontend since they are purely
presentational.

Works on both mobile (phone) and desktop (responsive design).


================================================================================
TECH STACK
================================================================================

Frontend  : React + Vite + Tailwind CSS (+ GSAP + Locomotive Scroll retained)
Backend   : Node.js + Express.js
Database  : MongoDB (via Mongoose) + MongoDB Atlas
Auth      : Clerk (Google OAuth only)
Payments  : Stripe (test mode only) — used only for the optional takeaway/
            delivery add-on, not for the core reservation experience
Images    : ImageKit
Emails    : Nodemailer (Gmail + App Password)
Errors    : Sentry (frontend + backend)
Charts    : Recharts (admin analytics)
Deploy    : Frontend → Netlify | Backend → Render | DB → MongoDB Atlas

================================================================================
DATABASE MODELS
================================================================================

--- User ---
{
  clerkId       : String (unique, required),
  name          : String,
  email         : String (unique),
  phone         : String,
  role          : String (enum: ['user', 'admin'], default: 'user'),
  createdAt     : Date
}

--- Category ---
{
  name          : String (required),          // Breakfast, Lunch, Dinner, Drinks
  slug          : String (unique),
  image         : String,                     // ImageKit URL
  createdAt     : Date
}

--- MenuItem ---
{
  name          : String (required),
  description   : String,
  price         : Number (required),
  category      : ObjectId (ref: Category),
  isAvailable   : Boolean (default: true),     // 86'd items toggle off same-day
  isVeg         : Boolean (default: false),
  isChefSpecial : Boolean (default: false),
  images        : [String],                   // ImageKit URLs
  ratings       : [ObjectId],                 // ref: Review
  averageRating : Number (default: 0),
  createdAt     : Date
}
NOTE: No stock/inventory tracking — this is a dine-in menu, not a shop.
      "isAvailable" is a simple on/off toggle for 86'd items.
NOTE: Add MongoDB text index on name + description for menu search.

--- Table ---
{
  tableNumber   : Number (unique, required),
  capacity      : Number (required),
  location      : String (enum: ['Indoor', 'Outdoor', 'Rooftop']),
  isActive      : Boolean (default: true)
}

--- Reservation ---                            (PRIMARY FEATURE)
{
  user          : ObjectId (ref: User),
  table         : ObjectId (ref: Table),
  guestName     : String,
  guestPhone    : String,
  date          : Date (required),
  timeSlot      : String (required),          // e.g. "7:00 PM - 9:00 PM"
  partySize     : Number (required),
  status        : String (enum: ['Pending','Confirmed','Seated','Completed','Cancelled']),
  specialRequest: String,
  createdAt     : Date
}
NOTE: Prevent double-booking — query existing reservations for same
      table + date + overlapping timeSlot before confirming.

--- Order ---                                  (OPTIONAL SECONDARY FEATURE)
{
  user          : ObjectId (ref: User),
  items         : [{ menuItem: ObjectId, qty: Number, price: Number }],
  orderType     : String (enum: ['Delivery','Takeaway']),
  totalAmount   : Number,
  status        : String (enum: ['Pending','Preparing','Out for Delivery','Ready for Pickup','Delivered','Cancelled']),
  paymentStatus : String (enum: ['Paid', 'Unpaid']),
  stripeSessionId: String,
  address       : { street, city, state, zip, country },  // only required when orderType is 'Delivery'
  emailSent     : Boolean (default: false),
  createdAt     : Date
}
NOTE: This model exists purely for the optional order-ahead add-on. If you
      want to keep the app strictly reservation-only for the portfolio demo,
      this entire Order feature (model, routes, pages) can be dropped without
      affecting anything else in the plan.

--- Review ---
{
  user          : ObjectId (ref: User),
  menuItem      : ObjectId (ref: MenuItem),
  rating        : Number (1–5),
  comment       : String,
  createdAt     : Date
}
NOTE: Only allow review if user has a completed reservation or delivered
      order that included this item.

--- Event ---
{
  title         : String (required),
  description   : String,
  image         : String,                     // ImageKit URL
  date          : Date (required),
  time          : String,
  seatsAvailable: Number,
  createdAt     : Date
}

--- Chef ---
{
  name          : String (required),
  role          : String,                     // Head Chef, Sous Chef, Pastry Chef
  bio           : String,
  photo         : String,                     // ImageKit URL
  socials       : { instagram, linkedin },
  createdAt     : Date
}

--- GalleryImage ---
{
  image         : String (required),          // ImageKit URL
  caption       : String,
  category      : String (enum: ['Food','Interior','Events']),
  createdAt     : Date
}

--- Testimonial ---
{
  guestName     : String (required),
  photo         : String,                     // ImageKit URL, optional
  rating        : Number (1–5),
  quote         : String (required),
  isFeatured    : Boolean (default: false),   // shown on Home page carousel
  createdAt     : Date
}

--- ContactMessage ---
{
  name          : String (required),
  email         : String (required),
  subject       : String,
  message       : String (required),
  isRead        : Boolean (default: false),
  createdAt     : Date
}


================================================================================
BACKEND API ROUTES
================================================================================

AUTH (Clerk Webhook Sync)
  POST  /api/auth/webhook          → Sync Clerk user to MongoDB on register/update

MENU
  GET   /api/menu                  → Get all menu items (search, filter, sort)
                                     Query params: ?search=&category=&sort=&veg=
  GET   /api/menu/:id              → Get single menu item detail
  POST  /api/menu                  → Create menu item (admin only) + ImageKit upload
  PUT   /api/menu/:id              → Update menu item (admin only)
  DELETE /api/menu/:id             → Delete menu item (admin only)

CATEGORIES
  GET   /api/categories            → Get all categories (Breakfast/Lunch/Dinner/Drinks)
  POST  /api/categories            → Create category (admin only)
  PUT   /api/categories/:id        → Update category (admin only)
  DELETE /api/categories/:id       → Delete category (admin only)

TABLES (admin-managed inventory of physical tables)
  GET   /api/tables                 → Get all tables
  POST  /api/tables                 → Add a table (admin only)
  PUT   /api/tables/:id             → Update a table — capacity/location/active (admin only)
  DELETE /api/tables/:id            → Remove a table (admin only)

RESERVATIONS (PRIMARY FEATURE)
  GET   /api/reservations/availability → Check available tables
                                     Query params: ?date=&timeSlot=&partySize=
  POST  /api/reservations          → Create reservation
  GET   /api/reservations/my       → Get logged-in user's reservations
  GET   /api/reservations          → Get all reservations (admin only)
                                     Query params: ?date=&status=
  PUT   /api/reservations/:id/status → Update reservation status (admin only)
  DELETE /api/reservations/:id     → Cancel reservation (user or admin)

ORDERS (OPTIONAL — takeaway/delivery add-on only)
  POST  /api/orders                → Place order + trigger Stripe checkout session
  GET   /api/orders/my             → Get logged-in user's orders
  GET   /api/orders/:id            → Get single order detail (order tracking)
  GET   /api/orders                → Get all orders (admin only)
  PUT   /api/orders/:id/status     → Update order status (admin only)
  GET   /api/orders/export         → Export orders as CSV (admin only)

REVIEWS
  POST  /api/reviews/:menuItemId   → Add review (must have a completed visit/order)
  GET   /api/reviews/:menuItemId   → Get menu item reviews

EVENTS
  GET   /api/events                → Get upcoming events
  POST  /api/events                → Create event (admin only) + ImageKit upload
  PUT   /api/events/:id            → Update event (admin only)
  DELETE /api/events/:id           → Delete event (admin only)

CHEFS
  GET   /api/chefs                 → Get all chef profiles
  POST  /api/chefs                 → Add chef (admin only) + ImageKit upload
  PUT   /api/chefs/:id             → Update chef (admin only)
  DELETE /api/chefs/:id            → Delete chef (admin only)

GALLERY
  GET   /api/gallery               → Get gallery images (filter by category)
  POST  /api/gallery               → Upload gallery image (admin only)
  DELETE /api/gallery/:id          → Delete gallery image (admin only)

TESTIMONIALS
  GET   /api/testimonials          → Get testimonials (?featured=true for Home carousel)
  POST  /api/testimonials          → Add testimonial (admin only)
  PUT   /api/testimonials/:id      → Update / feature a testimonial (admin only)
  DELETE /api/testimonials/:id     → Delete testimonial (admin only)

CONTACT
  POST  /api/contact                → Submit contact form → save + email admin
  GET   /api/contact                → Get all messages (admin only)
  PUT   /api/contact/:id/read      → Mark message as read (admin only)

ADMIN
  GET   /api/admin/stats           → Total reservations, covers, orders, users count
  GET   /api/admin/sales           → Reservations + orders per day/week/month (for chart)

STRIPE WEBHOOK (only relevant if the order-ahead add-on is used)
  POST  /api/stripe/webhook        → Handle Stripe payment success → update order
                                   → trigger order confirmation email via Nodemailer

================================================================================
AUTHENTICATION FLOW (CLERK — GOOGLE ONLY)
================================================================================

NOTE: In Clerk Dashboard → User & Authentication → Social Connections
      ONLY Google is enabled. Email/password and phone OTP are disabled.

1. User clicks "Continue with Google" (only sign-in option)
2. Clerk handles Google OAuth flow
3. On first login Clerk fires webhook → POST /api/auth/webhook
4. Backend receives webhook, verifies using svix, creates User in MongoDB
   with clerkId, name, email, role: 'user'
5. On every protected API request, frontend sends Clerk session token in header
6. clerkMiddleware on backend verifies the token using Clerk SDK
7. adminMiddleware additionally checks User.role === 'admin' in MongoDB


================================================================================
TABLE RESERVATION FLOW (PRIMARY FEATURE)
================================================================================

1. User goes to /reservation, selects date, time slot, and party size
2. Frontend calls GET /api/reservations/availability?date=&timeSlot=&partySize=
3. Backend queries Table + Reservation collections, excludes tables already
   booked for that date + overlapping timeSlot, and filters by capacity
4. Available tables/time slots are shown to the user
5. User submits the form → POST /api/reservations (status: Pending)
6. Backend re-validates availability at submission time (avoid race condition)
7. Reservation confirmation email sent via Nodemailer
8. Admin sees reservation in /admin/reservations, updates status
   Pending → Confirmed → Seated → Completed / Cancelled
9. User can view/cancel it from /my-reservations


================================================================================
OPTIONAL TAKEAWAY/DELIVERY ORDER FLOW (STRIPE, TEST MODE)
================================================================================

NOTE: This is a secondary add-on, not the core of the app. Skip this section
      entirely if you want to keep the portfolio project focused purely on
      reservations, menu, and content pages.

1. User adds menu items to their order from /order-online
2. User clicks "Proceed to Checkout"
3. Frontend calls POST /api/orders → backend creates order (status: Pending)
4. Backend creates Stripe Checkout Session (test mode) and returns session URL
5. Frontend redirects user to Stripe hosted test checkout page
6. User completes test payment using Stripe test card: 4242 4242 4242 4242
7. Stripe fires webhook → POST /api/stripe/webhook
8. Backend verifies webhook, updates order paymentStatus to 'Paid'
9. Backend sends order confirmation email via Nodemailer to buyer's email
10. User is redirected to order success page, order visible in /my-orders


================================================================================
RESERVATION & ORDER STATUSES
================================================================================

Reservation statuses (primary):
  Pending    → Reservation submitted, awaiting confirmation
  Confirmed  → Table confirmed by admin/system
  Seated     → Guests have arrived and are seated
  Completed  → Visit finished
  Cancelled  → Cancelled by user or admin

Order statuses (optional add-on):
  Pending → Preparing → Out for Delivery / Ready for Pickup → Delivered / Cancelled

Admin updates reservation status from /admin/reservations and order status
from /admin/orders (if enabled). Guests see current status on /my-reservations

================================================================================
IMAGE UPLOAD FLOW (IMAGEKIT) — WITH CATEGORY-BASED FOLDERS
================================================================================

CONCEPT:
  Every menu item image is stored inside a folder named after its category
  in ImageKit. Chef photos, event images, gallery images, and testimonial
  photos each get their own top-level folder. For example:
  - A Breakfast menu image → saved in /yummy/menu/breakfast
  - A Dinner menu image     → saved in /yummy/menu/dinner
  - A chef photo            → saved in /yummy/chefs
  - An event banner         → saved in /yummy/events
  - A gallery photo         → saved in /yummy/gallery/{food|interior|events}
  - A testimonial photo     → saved in /yummy/testimonials
  ImageKit automatically creates the folder if it does not exist yet.

IMAGEKIT FOLDER STRUCTURE:
  /yummy
  ├── /menu
  │   ├── /breakfast
  │   ├── /lunch
  │   ├── /dinner
  │   ├── /drinks
  │   └── /<any_new_category>     ← auto created when new category is added
  ├── /categories                 ← thumbnail images for each category card
  ├── /chefs                      ← chef profile photos
  ├── /events                     ← event banner images
  ├── /testimonials               ← guest testimonial photos
  └── /gallery
      ├── /food
      ├── /interior
      └── /events

HOW IT WORKS STEP BY STEP:

  MENU ITEM IMAGE UPLOAD (when admin adds/edits a menu item):
  1. Admin fills the menu item form and selects an image file
  2. Admin also selects the category for this item (e.g. "Dinner")
  3. Frontend sends the image file + category name to backend via
     multipart/form-data
  4. Multer middleware on backend receives the file as a buffer
  5. Backend converts the category name to lowercase with no spaces
     Example: "Fine Dining" → "fine-dining"
  6. Backend calls ImageKit upload with folder set to /yummy/menu/{categorySlug}
  7. ImageKit saves the image inside that folder and returns the full URL
  8. Backend saves that ImageKit URL into MenuItem.images[] in MongoDB
  9. Frontend displays the image using the ImageKit URL directly

  BACKEND CODE LOGIC (menuController.js):
    const categoryName = req.body.categoryName;
    const folderName = categoryName.toLowerCase().replace(/\s+/g, '-');

    const result = await imagekit.upload({
      file: req.file.buffer,             // file buffer from multer
      fileName: req.file.originalname,   // original file name
      folder: `/yummy/menu/${folderName}`  // category-based folder
    });

    // result.url is the ImageKit URL — save this to MongoDB
    menuItem.images.push(result.url);

  WHY THIS APPROACH:
  - All dinner images are together in ImageKit → easy to manage/delete by
    category
  - If a category is deleted, its folder can be cleaned up in ImageKit too
  - ImageKit dashboard shows organized folders instead of one messy root
  - No extra configuration needed — ImageKit auto-creates folders on upload
